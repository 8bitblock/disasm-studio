# Recorded execution path and Step Back

- At a native debugger pause, set the breakpoint you want to reach, then choose **Record** in the toolbar or **Debug > Record Execution Path**. Recording resumes the selected thread through the normal debugger step machinery. Ordinary Continue does not record a path.
- On the next breakpoint, exception, explicit Pause, or recording limit, choose **Step Back**. The **Execution History** inspector browses the recorded instruction addresses, captured code bytes and general-purpose registers in observation order. Repeated addresses remain separate rows, so loops and taken branches retain their observed order.
- Back/forward history controls only change the inspected record. The process remains at its actual debugger stop. The inspector labels that live stop separately; it never restores RIP, registers, stack or memory and never re-executes a historical instruction.
- Recording starts at the current pause. It cannot recover instructions that ran before recording began. The last captured RIP is a stopped instruction, not evidence that that instruction has executed.
- Recording uses native x86/x64 single stepping and is substantially slower than Continue. It records one selected thread's user-mode observations; it is not a complete multi-thread or kernel execution trace. Debugger interruptions and unsupported transitions can end a recording early, with a visible reason. Stop recording with the normal Pause control.
- Each run starts a fresh history with a maximum of 10,000 records. Reaching the limit pauses execution. The recording belongs to the exact PID, debugger session and selected thread, and is retired on detach or a new session. It is not durable project state.
- Instruction text is decoded from the bytes captured at each observation, with debugger-owned software breakpoint bytes restored in the capture. Missing bytes stay unavailable. Historical registers are read-only; historical stack/heap memory was not captured.
